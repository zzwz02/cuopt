# cuOpt MACA Porting

Use this skill together with `cuopt-developer` when the task is about making cuOpt build or run on MetaX C500 through MACA/cu-bridge. Keep the scope anchored to the repository state in front of you; old porting notes can contain useful facts, but should not override current code or current build logs.

## Porting Baseline

- Treat the C500 MVP as C++ core, C API, and `cuopt_cli` first. Python, REST server, gRPC, conda, and wheel packaging are out of scope unless the user explicitly brings them back.
- Preserve the RAPIDS-free baseline under `cpp/vendor/include`. Do not reintroduce runtime dependencies on upstream `rmm`, `raft`, `rapids_logger`, `cudf`, or NVIDIA CCCL.
- Use MACA's bundled Thrust/CUB where possible. Prefer `thrust::cuda::par` for execution policy compatibility; add local shims only for missing `cuda::` / `cuda::std::` APIs that cuOpt actually uses.
- Remember that C500 warp size is 64. In warp semantics, prefer `raft::WarpSize`, `lane_mask_t`, and `LANE_MASK_ALL`; audit fixed `32`, `0xffffffff`, `uint32_t` ballot masks, and `& 31`. Keep genuine 32-thread non-warp kernels only after checking correctness.

## Build Model

- Source `maca_env.sh` before MACA commands. It should select the workspace CMake 3.30.x toolchain and set `MACA_PATH`, `CUCC_PATH`, and `CUCC_TARGETS`.
- Always run C500 builds/tests with `export MACA_DIRECT_DISPATCH=1` (now set by `maca_env.sh`). MACA's default deferred/queued kernel dispatch causes cross-kernel ordering hangs and wrong results on C500 — e.g. PDLP batch tests (`simple_batch_*`) fail or the suite hangs when many solves run back-to-back in one process. Direct dispatch makes the launch path deterministic and is required for cuOpt correctness, not just performance.
- Configure with `cmake_maca` and build with `ninja_maca` or `make_maca`. It is expected that configure-time CUDA compiler detection sees real NVIDIA `nvcc`; cu-bridge swaps to MACA tooling during the build.
- Keep the build directory at `cpp/build_maca` unless the user asks for a different one.
- For one-off CUDA probes, compile with `/opt/maca/tools/cu-bridge/tools/pre_make nvcc`. Do not call `cucc` directly for ad hoc single-file checks; direct `cucc` should stay inside `cmake_maca` / `ninja_maca` / `make_maca` flows.
- After linking, check `ldd` for MACA libraries such as `libmcblas`, `libmcsparse`, `libmcruntime`, `libmcsolver`, and `libmcrand`. CUDA imported-target full paths can bypass cu-bridge remapping; prefer explicit MACA library targets or remappable `-l` names when validating a MACA build.

## Runtime Gotchas

- MACA `mcsparseCreateDnVec` rejects null `values` even for zero-length dense vectors. When constructing cuSPARSE dense-vector descriptors from possibly empty device buffers, provide a non-null device dummy pointer and include a diagnostic label in descriptor creation errors.
- Treat `cuopt_cli` exit status and output together. Some CLI paths can print an error even when shell status looks benign; an output line like `Error in solve_lp` or `cuopt_cli error` is a failed smoke.
- MACA can warn that `__launch_bounds__(..., minBlocksPerMultiprocessor)` ignores the second argument. Treat it as a performance warning unless the failing test points at occupancy-sensitive correctness.
- Old MACA CCCL lacks some newer libcudacxx APIs. Prefer small local compatibility shims over fetching NVIDIA CCCL, and keep shims scoped to APIs proven missing by build errors.
- **`cuda::std::span<bool const>` brace-init silently mis-compiles on MACA CCCL.** Constructing a span of `const bool` via brace-init — `cuda::std::span<bool const> s{ptr, count}` — is a narrowing list-initialization (`bool const*` → `bool`). Newer NVIDIA CCCL/CUDA (e.g. 12.9) *rejects it at compile time*; MACA's older CCCL *compiles it but builds a garbage span* (wild `.data()` like `0x2000000000004`, wrong `.size()`). It only breaks for `const bool` (not `int`/non-const `bool`). This corrupted cuOpt's vendored `raft::span` (`cpp/vendor/include/raft/core/span.hpp`, `base_{ptr,count}`), which backs the per-vehicle `order_match` (`span<bool const>`), causing a wild device pointer → ATU fault that crashed all GES routing on C500. Fix: use parenthesised direct-init `base_(ptr, count)` (forces the `(ptr,count)` ctor) — correct on every platform. Minimal A100-vs-C500 reproducer: `docs/dev/maca_span_bool_repro.cu` (build with/without `-DUSE_BRACE`). When a C500-only OOB points at a `span`/`device_span` of `bool`, suspect this first.
- Diagnosing a GPU **illegal memory access** (`mcErrorIllegalAddress` / Xnack/ATU fault) on C500: the fault is sticky — once it fires, the MACA runtime is disabled and every later CUDA call fails or hangs, so one OOB cascades into dozens of downstream test failures/hangs (run the suspected test in isolation to find the true trigger). The MACA UMD log pinpoints the offending kernel: read `~/mxlog/umd/trapInfo.*.log` (JSON, gives the mangled `kernelName` + `commandIndex`; `c++filt` to demangle) and `~/mxlog/umd/umd.*.log` (`grep trapping`/`kernelName`). `mcSanitizer` (`$MACA_PATH/tools/mcSanitizer`) only does `--trap-debug` and, in at least some containers, hangs on an `inotify_add_watch` of `/root/mcRpcPort.ini` — so to get the source line, fall back to recompiling the one offending `.cu` with `--generate-line-info` and/or injecting `printf` to bisect, or build it `-DASSERT_MODE` to activate `cuopt_assert` bounds checks (only helps if the OOB access is actually guarded). Known open item: `find_all_squeeze_pos` (GES squeeze) faults on C500 in the breaks path inside `node_t::total_excess_of_combine` (global transit/arc matrix read) — see `docs/dev/maca_c500_results.md` §4.
- When a multi-agent **workflow** investigates a GPU bug, agents may inject `printf`/instrumentation directly into tracked source (e.g. `cpp/src/routing/**`) and rebuild — `git status` after the workflow and `git checkout --` any unintended edits, then force-rebuild the affected objects, before committing or trusting the local `libcuopt.so`.
- Watch for **read-before-write device buffers** that are only safe because of fresh/zeroed allocations. On C500 the rmm pool readily hands back memory freed by a previous solve, so a buffer that is read before being fully written reads *that solve's garbage* instead of zeros — a cross-test/cross-solve contamination that passes in isolation but fails when a prior solve ran in the same process. Concretely: PDLP's saddle-point `current_AtY_`/`next_AtY_` (`cpp/src/pdlp/saddle_point.cu`) were left un-zeroed ("written by SpMV"), but in **batch** mode `update_solution` swaps them each step so the reflected-primal projection can read entries the current SpMM didn't rewrite; after a per-climber-objective batch solve freed its buffers, `simple_batch_different_constraint_bounds` / `simple_batch_everything_different` diverged to the iteration limit. Fix = zero-init both AtY buffers in the constructor. When a batch/PDLP test fails or hangs **only after another solve ran first**, suspect an uninitialized buffer, not the test. (`MACA_DIRECT_DISPATCH=1` does not mask these.)
- Cooperative grid launches (`cudaLaunchCooperativeKernel` + `cg::this_grid().sync()`) are unreliable on C500 and can hang the GPU at 100% util with no progress. Root cause: `cudaOccupancyMaxActiveBlocksPerMultiprocessor` only reports the warp/thread-limited occupancy (e.g. 16 for a 128-thread block at 2048 threads/SM) and ignores register/shared-mem pressure, **and** the true co-residency for a cooperative launch is even lower than that (empirically ~13-15/SM for a register-heavy kernel where the API says 16). The upstream idiom `grid = numSM * cudaOccupancyMaxActiveBlocksPerMultiprocessor(...)` therefore over-sizes the grid; the surplus blocks never become resident, and every `cg::this_grid().sync()` (and any hand-rolled global-memory arrival-counter barrier — same mechanism) deadlocks waiting on them. Unlike NVIDIA, MACA's `cudaLaunchCooperativeKernel` does **not** validate the grid size (NVIDIA returns `cudaErrorCooperativeLaunchTooLarge`), so the oversize silently hangs instead of erroring. This bit PDLP's PDLP_TEST `run_sub_mittleman` on large instances (e.g. `graph40-40`), but only in the `Methodical1` solver mode, which is the sole mode using `restart_strategy = 2` (`TRUST_REGION_RESTART`) and its `solve_bound_constrained_trust_region_kernel`. Small problems clamp the grid to 1 block and survive; large problems use the full bogus grid and hang. There is no reliable way to query the safe cooperative grid size on C500, so do not depend on it: prefer **host-driven multi-kernel** loops where each grid-sync point becomes a kernel-launch boundary (regular, non-cooperative launches at any grid size — blocks run in waves, kernel completion is the global sync). A single-block cooperative launch also avoids the deadlock but is far too slow (MACA's `cg::this_grid().sync()` has high per-call latency: graph40-40 went 0.3s → 7.2s, scpm1 → 69s).
- **Warp-cooperative spin-locks (`acquire_lock`/`release_lock`) deadlock *or leak* on C500.** `acquire_lock` (`cpp/src/utilities/cuda_helpers.cuh`) is the textbook Volta-ITS spin-lock: `while (atomicCAS(lock,0,1)) __nanosleep(100); __threadfence();`. It relies on **independent thread scheduling (ITS)**, which NVIDIA introduced in Volta (sm_70). C500 is **lock-step SIMT with no ITS** (`warp64`), so whenever **two or more lanes of the same warp** contend for the **same lock**, the warp cannot let the CAS winner make forward progress while the losers spin: it hangs at 100% util, **no trap, no error, graph-independent** (so it looks identical to a stuck kernel — check `~/mxlog/umd/trapInfo.*` is *stale* to rule out an OOB). Two distinct failure modes: (a) the winner is parked at the spin loop's reconvergence point and never reaches `release_lock` → classic deadlock; (b) in a *probing* lock (acquire → maybe advance to a different slot → retry, with mixed `return`/`continue`), a lane can win a CAS then be parked before its `release_lock`, **permanently leaking** that lock, so later probes onto that slot spin forever (observed signature: hundreds of lanes each stuck on their *own distinct* index). **Sites where same-warp lanes can contend for the same lock are affected** — sites guarded by `if (threadIdx.x==0)`, `if (lane_id==0)`, or a block-reduce winner (`reduction_idx==threadIdx.x`) are safe. **A site where each lane locks a *distinct* index is NOT automatically safe: it deadlocks too if there is *cross-block* contention on those locks.** When many blocks contend for the same lock array (e.g. `populate_cross_list_kernel`'s `route_pair_locks[first_route*n+second_route]` — distinct per lane within a block, but many blocks share a `first_route`), a lane that *wins* its CAS can be parked at the post-acquire point by the lock-step warp while a *sibling* lane spins on a lock currently held by another block; the winner then never reaches `release_lock`, so its locks stay held and every block waiting on them deadlocks. The trigger is load-dependent (needs enough blocks/contention), so it can pass on small inputs and hang only after a problem grows (e.g. the `test_re_routing` PDP re-optimization loop, which adds orders each iteration → more blocks → deadlock on a later solve, ~3-5% GPU util). All MIP `acquire_lock` sites are single-lane → safe; the affected sites are in routing local search. **Fixes** (`with_lock`/`with_lock_block` helpers added next to `acquire_lock`): for a **simple, single fixed lock**, do the critical section + release *inside* the winning-CAS branch — `while(!done){ if(atomicCAS(L,0,1)==0){ __threadfence(); crit; __threadfence(); atomicExch(L,0); done=true; } }` (fixed `record_candidate`/`record_candidate_thread_safe`/`prize_collection`/`perform_moves` scross, and `populate_cross_list_kernel`'s `route_pair_locks` — the latter was *missed* by the first spin-lock pass precisely because each lane locks a distinct index, which looked safe until the cross-block case above). For a **probing/multi-lock hash insert** (the cycle-finder `device_map_t::add`), in-branch release is *not enough* (mode (b) still leaks) — **serialize the routine across the warp's lanes** so only one lane is ever in the lock: `for (int turn=0; turn<raft::WarpSize; ++turn) if (raft::laneId()==turn) add_impl(...);` (no `__syncwarp`, so it is safe for divergent callers). This fixed `vehicle_breaks.uniform_breaks`, which hung in `find_vrp_moves`→`record_candidate` and then `find_best_negative_cycles`→`device_map::add`. To localize such a hang, bisect with `fprintf` at host-call boundaries (kernel-launch + `sync_stream`) and, once inside a kernel, add a bounded-iteration counter to each `while`-spin that `printf`s and breaks when it exceeds a sane cap — the loop that fires is the offender.
- **`cusparseXcsrsort` (mcsparse) traps on C500 under repeated async solves — replace it with CUB `DeviceSegmentedSort`.** `cusparseXcsrsort` dispatches internally to mccub kernels (an onesweep radix sort plus a permutation gather, `mcspGthrKernel`); mcsparse's *driving* of those kernels races on C500. In a normal async, repeated in-process solve they intermittently Xnack/ATU-fault (which disables the runtime and cascade-crashes the suite), yet the *exact same call replayed standalone — the dumped real inputs replayed 5×, fresh handle each — is fault-free*, `MACA_LAUNCH_BLOCKING=3` makes the whole solver pass, and raw mccub `cub::DeviceRadixSort::SortPairs` is also fault-free standalone. So it is mcsparse's internal driving, not mccub, not the data, not a cuopt buffer. Fix: sort the CSR column indices within each row with `cub::DeviceSegmentedSort::SortPairs` (segment begin/end = the CSR row offsets), reordering the matrix values, then `cudaStreamSynchronize` before the local work buffers free — the same primitive cuopt's manual `csr_to_csc_transpose` already uses on C500. This fixed `csrsort_cusparse` (`cpp/src/mip_heuristics/problem/problem_helpers.cuh`), which had cascade-crashed the Python LP suite on the 2nd in-process solve. Treat any `cusparseX*`/mcsparse call that runs every solve as a prime suspect when a fault only appears *after a prior in-process solve*. Repros: `docs/dev/mccub_csrsort_repro.cu` (replay real csrsort inputs), `docs/dev/mccub_onesweep_repro.cu` (raw mccub sort).
- **Any *host* TU that calls a CUDA runtime API on MACA device pointers must be compiled through cu-bridge — NVIDIA `libcudart` fails silently on MACA memory.** This bites the RAPIDS-free Python/Cython glue, not just kernels: cuOpt's RAPIDS-free LP/MILP path copies the solution `rmm::device_buffer` to a host numpy array with a plain `cudaMemcpy(..., cudaMemcpyDeviceToHost)` (`solver_wrapper.pyx::_device_buffer_to_numpy`). If that TU is built with the host compiler against **NVIDIA** `-lcudart` (the default of a stopgap g++ build script), the copy targets memory owned by the **MACA** runtime: `cudaMemcpy` returns `rc=1` (`cudaErrorInvalidValue`) **but the .pyx ignored the return code**, so `np.empty` keeps its uninitialized contents → `get_vars()`/`get_primal_solution()` come back all `inf`/garbage (and downstream warm-start, which re-feeds the bad solution, then hangs). It works on A100 only because there the memory *is* NVIDIA. Symptom signature: solver reports `Optimal` with sane objective, but the *returned arrays* are inf/garbage, **A100-clean / C500-only**, and a one-line `rc` print on the `cudaMemcpy` shows non-zero. **Fix = route the copy through cu-bridge's compile-time remap, not a hand-written `#ifdef` shim:** keep the `cudaMemcpy`/`cudaDeviceSynchronize` source verbatim and compile that TU with `pre_make nvcc` (+ cu-bridge CCCL include `tools/cu-bridge/include/cccl`, link `-lruntime_cu -lmcruntime` instead of `-lcudart`); cu-bridge's headers rewrite `cudaMemcpy→wcudaMemcpy` etc. at compile time. In `build_lp_modules_rapids_free.sh` this is the `CUOPT_RT_MACA=1` branch. Verify with `objdump -p <module>.so | grep NEEDED` → `libruntime_cu`/`libmcruntime` (no `cudart`) and `nm -uC` → `wcudaMemcpy`. General rule: on MACA, never link a TU that touches device pointers against NVIDIA `libcudart`; build it through `cmake_maca`/`make_maca`/`pre_make nvcc` so the runtime calls remap. And always check the return code of `cudaMemcpy`/`cudaDeviceSynchronize` — a silent failure here is invisible until the data is wrong.
- **C500 caps *total* (static + dynamic) shared memory per block at 64 KB, and `set_shmem_of_kernel` historically only checked the dynamic part — so a kernel can pass the check and still crash at launch.** Probe: `cudaGetDeviceProperties` → `sharedMemPerBlockOptin == 64 KB` on C500 (vs ~163 KB on A100); `cudaFuncSetAttribute(MaxDynamicSharedMemorySize, N)` succeeds for N ≤ 64 KB. But that attribute governs only the *dynamic* shared; if the kernel also has static `__shared__`, the **launch** needs static + dynamic, and once that total exceeds 64 KB `mcLaunchKernel` returns `mcErrorInvalidValue`. `find_all_squeeze_pos` (GES squeeze, `cpp/src/routing/ges/squeeze.cu`) requested 64548 B dynamic + 1028 B static = 65576 > 65536 → set_shmem returned `true` (dynamic alone fits) → the launch failed → the next `RAFT_CHECK_CUDA`/`cudaPeekAtLastError` threw `cudaErrorInvalidValue` and **crashed the solve** (a documented C500 routing fault). Fix: `set_shmem_of_kernel` (`cpp/src/utilities/cuda_helpers.cuh`) now queries `cudaFuncGetAttributes(...).sharedSizeBytes` and `cudaDevAttrMaxSharedMemoryPerBlockOptin` and returns `false` when `static + dynamic > device max`, so callers fall back / skip / raise `OutOfMemoryError` cleanly instead of crashing. (To actually *solve* a problem whose temp route exceeds 64 KB — e.g. one route of ~2000+ nodes — a kernel needs a global-memory temp-route fallback; the temp route is the dominant consumer via `route_t::get_shared_size`, which scales with route length.) NB: this is a *different* failure from a >64 KB kernel being silently skipped (non-fatal: the move just isn't taken) — both stem from the same 64 KB ceiling. Do **not** assume a routing host-hang is the 64 KB ceiling: measure (`CUOPT_DBG_SHMEM`-style instrumentation on `get_temp_route_shared_size`, or watch for the `mcFuncSetAttribute` flood) — `test_re_routing`'s hang looked like 64 KB (a rare, non-fatal `mcFuncSetAttribute` flood co-occurred) but its temp route was <20 KB and the real cause was the cross-move spin-lock deadlock above.
- **Running cuOpt's RAPIDS Python (routing/distance) on C500 needs MetaX's `mcdf` stack plus two compat shims.** mcdf ships cp310 wheels whose import names are mixed: `mcdf`→`cudf`, `mcpy`→`cupy`/`cupyx`, but `rmmx`→`rmmx` and `numbax`→`numbax` (not `rmm`/`numba`). Install all four with `pip install --no-deps` (so they don't drag in NVIDIA RAPIDS or perturb the LP env), then add the pure-Python deps `--no-deps` skipped: `fastrlock` (cupy), `llvmlite==0.39.1` (numbax = numba 0.56), and cudf's hard pins `pandas==1.5.3` / `pyarrow==10.0.1` / `protobuf==4.21.12`. cuOpt never `import rmm` directly (cudf uses rmmx internally), but its compiled routing/distance `.so` do `from numba import cuda` → add a `numba/__init__.py` shim in site-packages that aliases `numbax` (and its loaded submodules) into `sys.modules['numba*']`. And cupy's online JIT defaults its CUDA path to `/usr/local/cuda` and pulls NVIDIA's `cuda_fp16.h` (which `mxcc` can't parse — `NV_IS_DEVICE` undeclared); set **`CUDA_PATH=/opt/maca/tools/cu-bridge`** so it uses MACA's fp16 header. With that, `cudf`/`rmmx`/`numbax.cuda`/`cupy` all work and routing/distance solve through cudf inputs.
- **The cuOpt REST server runs LP *and* routing on C500; the one fix is `SIGCHLD=SIG_DFL` in the solver worker (`SIG_IGN` breaks MACA's runtime kernel recompile).** `python/cuopt_server` (FastAPI+uvicorn) needs only pure-Python deps (`fastapi uvicorn==0.34.* msgpack==1.1.2 msgpack-numpy==0.4.8 pydantic psutil jsonref requests`) plus the working `cuopt` on `PYTHONPATH`; launch `python cuopt_server/cuopt_service.py -p 5000 -i 127.0.0.1`. Two deploy gotchas: (1) if the box has an HTTP proxy (`http_proxy` set), `curl`/`requests` to a localhost port route through it and return **502** — use `--noproxy '*'` / `export no_proxy=127.0.0.1,localhost`; (2) the server enumerates GPUs with `nvidia-smi` (cosmetic — a co-installed A100 shows as GPU0), but the MACA-linked solver actually runs on the C500 (confirm with `mx-smi` showing the solver PID). **The bug:** routing requests made the forked solver worker flood `mcLaunchKernel: Returned mcErrorRecompile` → GES construction kernels never ran → `max_active_nodes=0` → squeeze `TPB=0` → a clean 400 `ValidationError: Number of threads should be greater than 0!` (LP worked because its PDLP kernels don't recompile). **Diagnosis:** `MXLOG_LEVEL=error,MCR=debug,MCC=debug` showed `mc_recompile.cpp: Because of max_block_size(512) is less than blockSize(1024), This kernel will recompile` then `MCC online build program ret(-1)` — i.e. C500 **runtime-recompiles** any kernel whose launch block size exceeds its compiled `max_block_size` (default 512), and that recompile *runs `mxcc` as a `fork+exec` subprocess and `wait()`s for it*. The worker (`cuopt_server/utils/solver.py::process_async_solve`) set `signal.signal(signal.SIGCHLD, signal.SIG_IGN)`, and on Linux **`SIG_IGN` on `SIGCHLD` auto-reaps children and makes `wait()` fail with `ECHILD`** → the `mxcc` wait fails → `build program ret(-1)` → `mcErrorRecompile`. A direct (non-server) process has no such handler, so the recompile succeeds — which is why routing worked directly but not via the server. **Fix:** change that worker's `SIGCHLD` to `SIG_DFL` (still ignores SIGCHLD but leaves `wait()` working). One line, no kernel changes; `mcErrorRecompile` drops to 0 and routing via REST returns correct solutions (validated: LP afiro Optimal/-464.7531/X01=80, routing cost 3.0/304/8). General rule on MACA: **never set `SIGCHLD=SIG_IGN` in any process that will run GPU kernels** — the runtime may `fork+exec mxcc` to recompile a kernel and needs `wait()`. (Perf aside: a 1024-thread launch on C500 always triggers this recompile since default `max_block_size=512`; `__launch_bounds__(1024)` or launching ≤512 avoids the recompile cost, but is not needed for correctness once SIGCHLD is fixed.)

## Diagnosing a C500-only OOB / fault — paradigm

The C500-only Xnack/ATU faults and hangs are almost always one of: a vendor kernel that races under async, a missing `cudaStreamSynchronize` before a buffer/handle is freed, a read-before-write of recycled rmm memory, or a silent mis-compile (e.g. the `span<bool>` gotcha). Apply these steps in order — each rules a class in or out, so you converge fast instead of guessing:

1. **Name the faulting kernel.** `~/mxlog/umd/trapInfo.*.log` gives the mangled `kernelName` + `commandIndex` (`c++filt` to demangle); cross-check `~/mxlog/umd/umd.*.log`. A *stale* trapInfo plus a 100%-util hang means a spin-lock/deadlock, not an OOB.
2. **Race vs deterministic — serialize with `MACA_LAUNCH_BLOCKING=3`.** It makes every launch synchronous. If the fault *disappears*, it is an **async race / ordering bug** (missing sync before a free, or a vendor kernel that races); if it *still faults serialized*, it is **deterministic** (bad data, real OOB, genuine bad kernel). Caveat: blocking is incompatible with CUDA-graph capture (`cudaStreamBeginCapture` errors), so if the path uses `manual_cuda_graph_t`, disable graphs first (next step).
3. **Inputs vs context — dump and replay standalone.** Instrument the cuopt call that launches the faulting kernel to dump its real inputs (scalar sizes + each device array, copied D2H *before* the call) to a file, then feed those exact bytes to the same library/kernel call in a tiny standalone program (compile one-off with `/opt/maca/tools/cu-bridge/tools/pre_make nvcc`). If standalone **reproduces**, the cause is the inputs/library-call — inspect the dumped data. If standalone is **clean**, it is the process/context — a race, recycled memory, or vendor global state, *not* the data.
4. **Bisect the context — one knob at a time.** Toggle and re-test: disable CUDA graphs (`manual_cuda_graph_t::run` → eager `work()`); force a single solver method (bypass `run_concurrent`'s OpenMP concurrency); zero/recompute a suspect buffer; run the A100 build under `compute-sanitizer --tool initcheck` (uninitialized global reads — invisible to `memcheck`) and `--tool memcheck` (OOB). Each toggle cleanly includes/excludes a cause. Worked example: the LP csrsort fault, `docs/dev/maca_c500_results.md` §4.3.
5. **Heisenbug caveat.** Instrumentation that adds a sync (a dump's `cudaStreamSynchronize`) can move or mask an async fault; a fault whose kernel or solve-index *shifts* when you change sync placement is itself strong evidence of a race, not bad data.

## Validation Ladder

1. Run environment smoke: `source maca_env.sh`, `cmake_maca --version`, and `mx-smi`.
2. Build incrementally with `PARALLEL_LEVEL=1 ninja_maca -C cpp/build_maca cuopt_cli -j1`; use higher parallelism only after memory headroom is clear.
3. Confirm a no-op rebuild before runtime smoke: `ninja_maca -C cpp/build_maca cuopt_cli -j1` should print `ninja: no work to do`.
4. Run CLI LP smoke on `datasets/linear_programming/afiro_original.mps`; expect `Optimal` and objective near `-4.64753143e+02`.
5. Run QP/barrier smoke on `datasets/benchmarks/maros_meszaros/QAFIRO.QPS`; expect barrier `Optimal` and objective near `-1.59078161e+00`.
6. Build and run a filtered C API smoke before attempting all tests. The full `C_API_TEST` includes MIP and callback cases that can be long-running or outside the C500 MVP scope.
7. Record MIP, routing, server, or gRPC failures explicitly rather than silently skipping device functionality.
